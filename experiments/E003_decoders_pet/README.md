# E003: Decoder comparison on Oxford Pet (pre-registered)

Status: **complete** (2026-10-14; 18 runs, 0 failures; code `9e5bba0`, frozen worktree).

## Questions
1. Does decoder capacity explain fastai's reputation? E002 stage A already shows no
   difference at equal recipe. This experiment checks the decoders inside one library with an
   identical encoder, data and recipe.
2. Where do ManySeg's decoders sit on the accuracy vs FLOPs Pareto front?

## Protocol
* Encoder resnet34 (`tv_in1k`), Pet 256², 20 epochs, recipe = the better E002 recipe
  (chosen by E002 val mIoU before E003 starts), seeds 0–2.
* Decoders: unet, fastai_unet, fpn, deeplabv3plus, upernet, segformer (default widths).
* Metrics: final val mIoU, val boundary F1, params, FLOPs at 256² (exact; hardware
  independent). Latency is measured separately and labelled contended.
* Budget: 18 runs, about 2 h on the shared 4090. No extra runs unless a difference larger than
  2 seed-SDs appears.

## Decision rule
A decoder is "better" only if its mean exceeds the reference `unet` by more than 2× the pooled
seed SD. Otherwise we report no detectable difference and prefer the cheaper decoder.

## Amendment (2026-10-14 10:40, before any E003 run)
E002 showed that the Pet validation split (376 images) cannot resolve differences of about 0.3
mIoU points, while the test split (3,669 images) can. Each E003 configuration is therefore
evaluated **once** on test as well (`--evaluate-test`). The decision rule still uses val. Test
results are reported alongside and are not used to choose anything. The same amendment applies
to E001b. Recipe chosen by the pre-registered rule: `fastai_like`.

## Interpretation
* **fastai's advantage comes from its decoder, and ManySeg reproduces it.** With an identical
  encoder, data and recipe, ManySeg's `fastai_unet` port is +0.40 test mIoU over `unet` (t 7.3).
  That matches the +0.3 measured with the real fastai library in E002. On val (376 images) the
  difference is +0.14 (t 2.0), below the pre-registered 2-SD rule. The cost is 4.0× the FLOPs
  and 1.7× the parameters.
* **UPerNet ≈ U-Net** (+0.07 test, t 2.1) at 2.3× the FLOPs. It is not worth it on Pet.
* **Stride-4 decoders lose 0.4–1.1 points** on this boundary-heavy, low-resolution task
  (SegFormer −0.4, FPN −0.5, DeepLabV3+ −1.1). They are cheaper (10–14 GFLOPs). Caveat:
  DeepLabV3+ here reads an undilated stride-32 encoder (rates 6/12/18). SMP's default dilates
  to output stride 16, which is available via `backbone_kwargs={"output_stride": 16}` but was
  not tested.
* **Pareto front (test mIoU vs FLOPs):** deeplabv3plus (10.4) → segformer (12.0) → unet (15.7)
  → fastai_unet (63.1). fpn and upernet are dominated.

## Decision
`unet` stays the default (best quality per FLOP among the near-equal options). `fastai_unet` is
documented as the high-capacity option: +0.3–0.4 mIoU for 4× decoder compute. No new
architecture work is justified by this experiment. The open question (from E002) is whether
fastai's gain comes from capacity alone or from its specific design (skip BN, pixel shuffle,
input cross). A width-matched U-Net would separate the two and is a candidate follow-up.
